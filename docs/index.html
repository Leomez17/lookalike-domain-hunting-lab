Key finding. onlinehmrc[.]com sits outside HMRC's defensive registrations. It is privacy-masked, about one year old, mail-enabled, carries a fresh Let's Encrypt certificate and is live on a Frankfurt-hosted server, yet had no public scan history. The page was an untitled 1 KB placeholder: infrastructure prepared but not yet serving a lure. Recommended: block, takedown via the organisation's process, and monitor the certificate renewal due around 30 Oct.

Triage pipeline

  1. Generate: dnstwist against hmrc.gov.uk (baseline) and hmrc.com with fraud keywords and alternative TLDs.
  2. Cluster: separate defensive registrations by shared IP and name servers (Com Laude / Demys).
  3. Mail readiness: flag domains with MX records configured.
  4. Registration: WHOIS age, registrar and registrant, looking for young + privacy proxy + retail registrar.
  5. Certificates: Cert Spotter CT API (crt.sh was returning 502).
  6. Hosting and content: dig, IP WHOIS, abuse contacts and a private urlscan.io scan. No suspect site was browsed directly.

Analyst judgement

  • Defensive registrations first: the obvious fraud keywords (hmrc-refund, verify-hmrc, claimhmrc…) are already HMRC-owned, so hunting effort goes to the gaps.
  • Hypothesis revised on evidence: a certificate pivot initially suggested a compromised business host. Later DNS showed that domain was parked, so the assessment was updated to "shared hosting account controlled by the same operator".
  • No false links: shared Namecheap parking IPs were not treated as a connection.
  • Source resilience: crt.sh outage → Cert Spotter; a single DNS snapshot missed a live A record, so high-priority domains need scheduled re-resolution.
  • OPSEC lesson: one early urlscan submission was public. Scans of suspected infrastructure should be private by default.
